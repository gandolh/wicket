# Wicket corpus: rules

This directory is the project's wiki and work tracker, kept by the LLM. The
owner curates sources and asks questions. The LLM writes the synthesis and
tracks the work. Anything worth keeping from a chat goes back in here.

The repo is public. Everything here is written for a stranger reading it on
GitHub: no secrets, no machine paths, no domain, no personal details.

The repo-wide hard rules and the brief-board steps are in the root
[CLAUDE.md](../CLAUDE.md), with the commands.

## Layout

```
corpus/
  CLAUDE.md    this file
  index.md     catalog, generated by `bash corpus/lint.sh --index`
  routing.md   which skill runs the work, which layer answers which question
  lint.sh      health check; exits non-zero on failure
  log.md       chronological record, newest last
  todos/       captured ideas, as prose, before they are specs
  briefs/      numbered work specs: todo/ done/ superseded/
  wiki/        the synthesis pages
```

## Retrieval budget

1. Read `index.md` first and triage on the `summary:` lines.
2. Open at most 2-3 wiki pages. Needing a fourth means a page straddles two
   topics or a summary is vague. Fix that instead of reading more.
3. Don't read `briefs/` or `todos/` wholesale. `wiki/status.md` has the
   per-area snapshot and the todo list. Open a brief only for the spec behind
   a specific piece of work.

## The corpus is the why, the code is the what

The wiki records why the code is shaped the way it is: decisions, intent,
history. It does not answer "who calls X" or "what breaks if I change Y". Those
go to `grep -rnw` and the typecheck. `routing.md` has the table.

## Frontmatter

Every page in `wiki/` opens with exactly two keys:

```
---
summary: <what question this page answers, written for an agent deciding whether to open it>
updated: <YYYY-MM-DD>
---
```

`index.md` is generated from the summaries. Never edit the catalog by hand.

## Briefs

- A todo becomes a brief at `briefs/todo/<NN>-<slug>.md`. NN is the max across
  all three brief dirs plus one, two digits. Numbering never restarts.
- Finished work moves to `briefs/done/` with the same number and a short
  outcome note added at move time. After that the file is immutable.
- Work later undone moves to `briefs/superseded/` with a one-line note on top.
  Never renumber, never rewrite a done brief.
- Briefs run in number order. `wiki/status.md` gives a dated snapshot per area.

## Source of truth, when things disagree

1. The code wins over any wiki claim. Verify a path or function before acting
   on what a page says about it.
2. A brief in `done/` wins over the wiki until the wiki catches up.
3. `wiki/decisions.md` wins over `wiki/status.md` for choices nobody has
   formally revisited. Changing a recorded decision needs an explicit revisit
   and a `log.md` entry.
4. `wiki/api.md` is the contract other repos build against. Changing it means
   telling the owner, because just-a-bot's and ro-housing's briefs quote it.

## Decisions and glossary

- Record a decision only if it is hard to reverse, surprising without context,
  and a real trade-off with named alternatives. Give the date, what was
  rejected and the reason.
- Glossary entries are definitions only, one or two sentences, with an
  `_Avoid_:` line listing the synonyms they replace. A term used two ways is
  two terms.

## Writing

- Standard relative markdown links. Code links from `wiki/` look like
  `../../server/src/app.ts`.
- Absolute dates only (`2026-11-04`), never "last week".
- One concept per page. Split a page past 200 body lines.
- Other repos are named, never pathed: "brief-board", "Ward" (the `wzd_auth`
  repo), "vps-deploy". No `../sibling` links, no home directories, no
  usernames, no domain (write `<your domain>` or `example.com`).
- Code comments don't cite brief numbers ("brief 05", "(brief 03)"). Say what
  the code does and why; the history belongs in `log.md`.
